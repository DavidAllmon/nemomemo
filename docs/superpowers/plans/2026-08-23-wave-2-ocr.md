# OCR on Image Attachments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On image upload, extract text with tesseract.js (WASM) into a new `attachment.extracted_text` column that feeds full-text search — screenshots, whiteboards, and receipts become findable. `NEMOMEMO_OCR=0` opts out; docs updated in the same release (public-docs-rule).

**Architecture:** Migration `0007` adds `attachment.extracted_text` plus an `attachment_fts` external-content FTS5 table synced by triggers (same pattern as `memo_fts`). A new `services/ocr.ts` exposes an injectable `OcrEngine` (production: lazy module-shared tesseract.js worker with traineddata cached under the data dir — Docker image stays slim; tests: fakes) and an `OcrQueue` that serializes jobs process-wide (one WASM recognize at a time even in cloud mode) and fire-and-forgets after the upload response. `filter-sql`'s `contains` compilation ORs in matches from linked attachments' extracted text. No web UI changes — this ships as search reach.

**Tech Stack:** tesseract.js (server dependency — `pnpm deploy --prod` puts it in the Docker image), FTS5 external-content + triggers, AppDeps injection (mirrors `mailer`).

**Spec:** `docs/ROADMAP.md` § Wave 2 (OCR row) + cloud-execution-handoff memory. Facts verified 2026-08-23: `createWorker(langs, oem, { langPath, cachePath })`; traineddata auto-downloads from jsDelivr (~a few MB per language) unless `langPath` points elsewhere; `cachePath` persists it.

- Search results remain guarded by the OUTER memo WHERE in `listMemoRows` — the attachment subquery only widens the match set for memos the viewer could already see. An attachment can never out-scope its memo (`a.memo_id = memo.id` join).

- OCR failures must never fail an upload or crash the process: queue catches, warns, moves on.
- Reef-voice untouched (no user-facing copy in this release beyond docs/changelog).

- [ ] **Step 2:** Run — FAIL (`no such table: attachment_fts`).
- [ ] **Step 3:** Migration `0007_ocr.sql`:

```sql
-- OCR text for image attachments, searchable via FTS5 (same external-content
-- + trigger pattern as memo_fts in 0006).
ALTER TABLE attachment ADD COLUMN extracted_text TEXT NOT NULL DEFAULT '';

CREATE VIRTUAL TABLE attachment_fts USING fts5(
  extracted_text,
  content='attachment',
  content_rowid='id',
  tokenize="unicode61 remove_diacritics 2"
);

CREATE TRIGGER attachment_fts_after_insert AFTER INSERT ON attachment BEGIN
  INSERT INTO attachment_fts(rowid, extracted_text) VALUES (new.id, new.extracted_text);
END;

CREATE TRIGGER attachment_fts_after_delete AFTER DELETE ON attachment BEGIN
  INSERT INTO attachment_fts(attachment_fts, rowid, extracted_text) VALUES ('delete', old.id, old.extracted_text);
END;

CREATE TRIGGER attachment_fts_after_update AFTER UPDATE OF extracted_text ON attachment BEGIN
  INSERT INTO attachment_fts(attachment_fts, rowid, extracted_text) VALUES ('delete', old.id, old.extracted_text);
  INSERT INTO attachment_fts(rowid, extracted_text) VALUES (new.id, new.extracted_text);
END;

INSERT INTO attachment_fts(rowid, extracted_text) SELECT id, extracted_text FROM attachment;
```

Add `extractedText: text('extracted_text').notNull().default('')` to the attachments table in `schema.ts` (match the file's existing drizzle idioms exactly).

- `interface OcrEngine { recognize(absolutePath: string): Promise<string> }`
- `class OcrQueue { constructor(db: Db, uploadsDir: string, engine: OcrEngine); enqueue(attachmentId: number): void; idle(): Promise<void> }` — process-wide serialized (module-level promise chain), errors caught + warned, writes `extracted_text` via raw UPDATE (fires the FTS trigger).
